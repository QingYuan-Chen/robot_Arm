# Star Arm 102-LD → reBot B601 Python SDK 实时主从跟随设计

## 1. 目标与边界

在独立仓库中实现一个不依赖 ROS 2 的 Python SDK 实时跟随程序：读取
Star Arm 102-LD 引导臂的 J1～J6，并驱动 reBot B601-DM 从臂按已通过 RViz
目视验收的方向映射实时跟随。

本里程碑包含六轴真机实时跟随、从臂反馈监控、目标整形、异常保持、受控返回
`safe_home`、到位验证以及正常失能。它不包含夹爪跟随、重新置零、自动标定、
ROS 2 接口、MoveIt 规划或环境碰撞检测。

Python 串口循环提供的是 `soft real-time / 软实时` 控制，不宣称硬实时保证。
目标循环频率为 50 Hz，并记录实际周期、超时和最大抖动，以实测结果判断是否达标。

所有实现只放在 `/home/a/project/Star-Arm-102-sdk-test`。本功能可以只读参考
`/home/a/project/rebot_Arm` 中已经使用的安全参数和控制顺序，但不修改该仓库，
也不在运行时依赖其源码或 ROS 安装空间。

## 2. 已确认的硬件和坐标约定

| 角色 | 设备 | 串口 | 波特率 | 节点 |
| --- | --- | --- | ---: | --- |
| 引导臂 | Star Arm 102-LD | `/dev/ttyUSB0` | `1_000_000` | FashionStar ID `0..6` |
| 从臂 | reBot B601-DM | `/dev/ttyACM0` | `921_600` | 达妙 ID `0x01..0x07` |

跟随只使用引导臂 ID `0..5` 和从臂 `joint1..joint6`。夹爪 ID 6/`0x07`
只允许读取状态，不发送模式、使能、失能、位置、速度或力矩命令。

方向以从臂坐标为准。经过 RViz 全六轴虚拟验证并由操作员确认的符号向量是：

```text
joint1  joint2  joint3  joint4  joint5  joint6
  -1      -1      +1      +1      +1      -1
```

程序启动时分别采集引导臂基线 `qL0` 和从臂当前基线 `qF0`。原始跟随目标为：

```text
q_raw[i] = qF0[i] + sign[i] * radians(q_leader[i] - qL0[i])
```

六轴比例均为 `1.0`。绝不把引导臂绝对角度直接写给从臂。启动后不自动回
`safe_home`；从臂当前反馈位置就是第一帧保持目标，因此开始跟随时不得跳变。

## 3. 方案选择

### 3.1 直接使用 `motorbridge` 的自定义控制循环（采用）

引导臂继续使用 `fashionstar_uart_sdk` 监视接口；从臂直接使用 `motorbridge`
注册六个机械臂电机，显式执行模式、使能、命令、反馈、保持、返回和失能。
所有 `CallError` 和反馈异常必须向上传递给安全状态机，不能被吞掉。

该方案满足 Python SDK 优先、无需 ROS 2、低延迟和失败路径可审计的要求。

### 3.2 使用上游高层 `RobotArm`（不采用）

上游高层封装可以快速发送 `pos_vel`，但部分模式、使能和命令路径捕获错误后只打印
或直接忽略，`disconnect()` 还会自动停止、失能和关闭。实时跟随需要区分“健康状态下
保持”和“严重故障保护停机”，因此不能让这些生命周期动作隐藏在高层封装里。

### 3.3 Python 引导臂配合 ROS 2 从臂控制器（暂不采用）

该方案可复用现有 ROS 控制器，但与当前先完成纯 Python SDK 验证、后续再接入 ROS 2
的顺序不符。ROS 2 版本作为独立后续里程碑，不与本次实现混合。

## 4. 组件与职责

在现有 `Python_SDK/rebot_b601_mapping/` 中增加以下小模块，不改变只读命令的语义：

- `live_config.py`：加载并严格校验实时参数、关节限位、映射符号和 `safe_home`。
- `command_shaper.py`：根据时间步执行位置边界、相对偏移、速度、加速度和加加速度
  约束；不接触串口。
- `follower_controller.py`：唯一拥有从臂串口和六轴电机句柄；负责只读校验 POS_VEL
  配置、首帧保持、使能确认、周期命令/反馈、保持、受控回位和失能验证。
- `safety_supervisor.py`：根据输入新鲜度、反馈、状态码、跟踪误差和控制周期驱动安全
  状态机；不直接调用 SDK。
- `live_follow.py`：编排引导臂采样、从臂控制循环、日志和操作员停止请求。
- `cli.py`：新增明确的 `follow` 命令。现有 `snapshot`、`calibrate-directions` 和
  `rviz-preview` 继续保持只读。
- `live_follow.example.json`：保存本设计确定的默认值，并标明映射验收级别为
  `rviz_visual_accepted`，不得写成“真机方向标定已通过”。
- `tests/`：用伪时钟、伪读取器和伪电机覆盖状态机、目标整形和全部退出路径。

引导臂采样线程只发布带单调时钟时间戳的最新完整样本。从臂控制循环是
`motorbridge` 总线的唯一写入者，以免命令和反馈轮询相互竞争。线程之间只交换最新
不可变快照、停止请求和结构化故障事件，不共享 SDK 对象。

## 5. 参数来源和初始值

实时跟随复用网页遥操作和现有运动安全配置中的已用阈值，而不是另造一套数值。受保护
回位使用网页遥操作中操作员记录的六轴安全姿态。该坐标只表示 `safe_home / 停放安全位`；
实时跟随从两臂当前姿态直接启动，不设置或要求 `follow_ready / 跟随就绪姿态`：

```text
[-1.549363136291504, 0.01659393310546875, -0.02002716064453125,
 -0.00858306884765625, 0.10395240783691406, 0.00133514404296875]
```

| 参数 | 初始值 | 用途 |
| --- | ---: | --- |
| 控制频率 | `50 Hz` | Python SDK 跟随目标周期 |
| 默认跟随速度 | `0.5 rad/s` | 对应网页连续按键默认速度 |
| 可配置速度硬上限 | `1.5 rad/s` | 对应网页执行接口上限 |
| 最大加速度 | `5.0 rad/s²` | 对应现有 MoveIt/回放限制 |
| 最大加加速度 | `20.0 rad/s³` | 对应现有 MoveIt/回放限制 |
| 最大跟踪误差 | `0.25 rad` | 对应现有回放监视阈值 |
| 跟踪误差持续时间 | `0.30 s` | 防止单个抖动样本误触发 |
| 引导臂样本超时 | `0.5 s` | 对应遥操作输入超时 |
| 从臂反馈严重超时 | `0.25 s` | 沿用现有驱动的反馈过期量级 |
| 安全位到位误差 | `0.02 rad` | 对应现有 `safe_home` 到位容差 |
| 安全位到位速度 | `0.05 rad/s` | 排除只经过目标但尚未稳定的情况 |
| 安全位最终稳定时间 | `1.0 s` | 对应现有最终保持时间 |
| 安全位返回超时 | `30.0 s` | 对应现有驱动的 `safe_home` 超时 |

从臂位置边界直接使用网页遥操作从 URDF 加载、并由硬件层再次检查的真实关节范围：

```text
joint1 [-2.80,  2.80]
joint2 [-3.14,  0.02]
joint3 [-3.14,  0.00]
joint4 [-1.87,  1.57]
joint5 [-1.57,  1.57]
joint6 [-3.14,  3.14]
```

正常跟随、启动反馈和固定回位终点都按上述同一组网页边界检查，不再额外缩进或动态扩展。
边界端点本身允许使用；若原始映射目标越过真实位置边界，程序拒绝该目标并进入可恢复异常
流程，不采用静默裁剪。静默裁剪会破坏主从姿态对应关系，并可能在引导臂回到范围内时产生
突变。加载器显式拒绝仍含旧 `joint_margin_rad` 或 `max_relative_delta_rad` 字段的配置，
避免操作员误以为这些额外限制仍然生效。

默认速度 `0.5 rad/s` 可由命令行或配置调高，但加载阶段就必须拒绝任何超过
`1.5 rad/s` 的值。J4～J6 的固有 MoveIt 速度上限为 `1.8 rad/s`，因此统一的
`1.5 rad/s` 硬上限不会超过六轴中较低的一组既有速度边界。

POS_VEL 环路参数直接复用当前从臂 `arm.yaml` 中的已用数据，避免依赖电机里可能遗留的
未知寄存器值：

| 关节 | `vel_kp` | `vel_ki` | `pos_kp` | `pos_ki` |
| --- | ---: | ---: | ---: | ---: |
| J1～J3（4340P） | `0.0125` | `0.004` | `150.0` | `0.5` |
| J4～J6（4310） | `0.0008` | `0.002` | `50.0` | `1.0` |

实时跟随启动阶段要求 RID 10 已是 `POS_VEL` 模式，并只读确认 RID 25～28 的现有增益
均为有限非负数，不要求与上述主项目 YAML 参考值精确相等。启动不写寄存器，也不调用
可能改写模式的 `ensure_mode()`；任一读取失败、模式错误或增益无效都在使能前终止。
运行时下发的 `vlim` 使用本设计的 `0.5 rad/s` 默认值和 `1.5 rad/s` 硬上限，而不是
`arm.yaml` 中用于一般控制的 `5.0/3.0 rad/s`。

## 6. 启动、使能和实时数据流

### 6.1 静态启动检查

1. 要求 `/dev/ttyUSB0` 和 `/dev/ttyACM0` 的设备身份与打开前一致，且未被其他进程占用。
2. 如果 ROS 控制器仍占用 `/dev/ttyACM0`，拒绝启动；程序不自动终止或抢占该进程。
3. 打开两个串口并读取稳定样本。引导臂 J1～J6 必须完整、有限且新鲜；从臂六轴必须
   完整、有限、位于真实关节限位内，且启动状态全部为 `status_code=0`。此处得到从臂
   基线 `qF0`；引导臂样本只用于健康检查，不作为最终 `qL0`。
4. 夹爪状态可记录，但无论其位置如何都不纳入映射。若夹爪不是失能状态，拒绝启动，
   防止遗留控制器仍在施加夹持命令。
5. 输出端口、映射、两侧基线、速度和安全阈值。`follow` 命令必须带显式真机运动确认
   选项；缺少确认时只完成静态检查并退出。
6. 获得显式真机运动确认后、使能前，只读核对六轴 POS_VEL 模式，并确认环路增益有限
   且非负；读取失败、模式错误或增益无效时不使能、不发送关节命令。

### 6.2 无跳变使能

1. 在从臂仍失能时，把六轴当前反馈 `qF0` 写入内部保持目标，不要求移动到 ready 位。
2. 只读配置校验已经确认六轴均为 POS_VEL 模式；使能阶段不再写寄存器或切换模式。
3. 使能六个机械臂关节，不使能夹爪。
4. 读取六轴反馈并确认全部为 `status_code=1`。
5. 立即以 `qF0` 和默认速度限制启动周期发送，在连续反馈正常后进入 `ENABLED_HOLD`。
6. 在六轴已经稳定保持 `qF0` 后重新采集引导臂稳定样本，并将其固定为 `qL0`，再进入
   `FOLLOWING`。使能期间引导臂的移动不会被解释为待追赶的大幅目标。

若使能只成功了一部分，程序请求所有六轴失能并验证 `status_code=0`。只有在尚未开始
实际跟随、且仍能验证机械臂处于初始基线附近时，才允许该回滚；如果验证失败，进入
人工恢复状态并明确报告每个关节的状态，不谎报已安全关闭。

### 6.3 50 Hz 跟随循环

每个周期执行：

1. 取得最新完整引导臂样本并计算 `q_raw`。
2. 先验证有限值、相对偏移和位置边界。
3. 以实际 `dt` 对上周期命令做速度、加速度和加加速度整形，得到连续的 `q_cmd`。
4. 向六轴发送 POS_VEL `q_cmd` 和当前速度上限。
5. 请求并轮询六轴反馈，验证位置、速度、状态码和时间戳。
6. 计算 `abs(q_feedback - q_cmd)`。跟踪误差只对整形后的命令计算；引导臂移动过快造成的
   `q_raw - q_cmd` 仅作为主从滞后记录，不能误判为电机跟踪故障。
7. 写入 JSONL 日志并等待下一周期。循环不得用累计 `sleep(0.02)` 漂移，而应以单调时钟
   计算绝对截止时间。

## 7. 安全状态机与异常处理

主要状态如下：

```text
DISCONNECTED
  -> PRECHECK
  -> ENABLED_HOLD
  -> FOLLOWING
  -> RECOVERABLE_HOLD
  -> RETURNING_SAFE_HOME
  -> VERIFYING_SAFE_HOME
  -> DISABLING
  -> DISCONNECTED
```

另有 `OPERATOR_RECOVERY` 和 `CRITICAL_STOP` 两个非正常终态。

### 7.1 可恢复异常

以下情况进入 `RECOVERABLE_HOLD`：

- 引导臂样本缺失、非有限或超过 `0.5 s` 未更新；
- 映射目标越过网页位置边界；
- 跟踪误差超过 `0.25 rad` 并持续 `0.30 s`；
- 控制循环连续 3 个周期错过截止时间，但从臂通信、反馈和状态码仍然健康；
- 第一次 Ctrl+C、正常停止请求或可处理的程序级异常。

处理顺序固定如下：

1. 停止更新跟随目标，把最后一次有效从臂反馈作为新的保持目标；如果同周期反馈不可用，
   使用最后一个已经成功发送的 `q_cmd`。
2. 保持六轴使能并继续发送静止目标，确认状态仍为 `status_code=1`。
3. 以同一速度、加速度和加加速度约束，从保持位置生成到网页遥操作所用操作员记录
   `safe_home` 的平滑关节空间返回序列；该固定终点与普通跟随目标使用同一组网页真实限位。
4. 返回期间持续检查反馈和跟踪误差。该纯 Python 路径不具备环境碰撞规划能力，运行前
   必须保证工作空间无障碍物；不能把“终点无自碰”描述为“整条返回路径已规划无碰撞”。
   回位起点和每周期反馈还必须位于网页真实关节闭区间；越界时不得继续生成回位序列，
   也不得以到位容差为由判定成功或自动失能，而应使用最后一次已发送的界内命令保持使能
   并转入人工恢复。使能接口必须分别返回实际已发送命令和发送后的反馈，防止使能后漂移
   反馈覆盖最后安全命令。最终从臂命令出口在使能保持和每次周期写入前复用同一组边界检查；
   正常跟随每周期反馈越界也按可恢复故障处理，并保留原始越界原因。
5. 返回过程最多允许 `30.0 s`。六轴误差均小于 `0.02 rad`、绝对速度均小于
   `0.05 rad/s`，并连续保持 `1.0 s` 后，才允许失能。
6. 失能后读取并验证六轴 `status_code=0`，然后关闭句柄。

若受控返回失败，但通信、反馈和六轴状态仍健康，程序进入 `OPERATOR_RECOVERY`：继续
保持使能和当前位置，不执行失能、不关闭串口，也不因异常处理再次抛错而跌落到通用
`finally: disable`。程序持续显示失败原因，等待操作员明确选择重新回位或紧急停机。

### 7.2 严重异常

以下情况意味着保持力矩不再可信，进入 `CRITICAL_STOP`：

- 从臂反馈超过 `0.25 s` 未刷新；
- 任一机械臂电机 `status_code` 不为预期使能值；
- 控制器或电机报告故障；
- 从臂串口断开或设备身份变化；任一六轴命令写入失败，或未能在 `0.25 s` 内完成一次
  全六轴有效反馈事务；
- 操作员发出明确的紧急停止请求。

此时不尝试盲目返回 `safe_home`。程序停止生成变化目标；若控制通道仍可用，先发送一次
最后位置保持请求，再请求六轴保护性失能并验证结果。若通信已经不可用，程序不能虚构
失能成功，只能保留最后已下发的 POS_VEL 目标、报告“失能结果未知”，并要求操作员使用
物理急停或断电手段处理。

严重异常路径和显式紧急停机是仅有的“从臂不在 `safe_home` 也可以请求失能”的情况。

## 8. 正常停止与信号语义

- 第一次 Ctrl+C：等同正常停止，执行“保持当前位置 → 返回 `safe_home` → 验证 → 失能”。
- 在 `OPERATOR_RECOVERY` 中输入重试：从当前保持位置重新尝试受控返回。
- 在 `OPERATOR_RECOVERY` 中明确输入紧急停机，或收到第二次 Ctrl+C：进入
  `CRITICAL_STOP` 并请求保护性失能。
- 仅关闭 Python 句柄不代表电机已失能。日志和终端必须分别报告“句柄已关闭”和
  “六轴已验证失能”。

程序不得使用上游 `RobotArm.disconnect()` 或控制器上下文管理器作为通用清理逻辑，
因为它们会把失能隐藏在退出动作中。句柄关闭由安全状态机在明确的生命周期结果后执行。

## 9. 日志与可观测性

默认把日志写到用户指定路径或 `/tmp`，不在仓库内产生未跟踪运行数据。每条 JSONL 至少包含：

- 单调时间戳、状态机状态和循环周期；
- 引导臂原始角度、`qL0` 和角度增量；
- `q_raw`、整形后的 `q_cmd`、从臂反馈位置和速度；
- 六轴跟踪误差、主从滞后、状态码和反馈年龄；
- 当前速度/加速度限制；
- 状态转换、停止来源、异常分类、回位结果和失能验证结果。

终端以固定频率刷新摘要，不能每个 50 Hz 周期打印一整行而拖慢控制循环。原始异常保留
类型和信息，但面向操作员的首要消息使用简体中文。

## 10. 测试策略

### 10.1 无硬件自动化测试

- 验证六轴符号、度到弧度和相对基线公式。
- 验证第一帧目标严格等于从臂启动反馈。
- 验证网页真实位置边界端点可用、范围外目标拒绝、`1.5 rad` 相对偏移拒绝以及
  `0.5/1.5 rad/s` 速度配置边界。
- 验证 J1～J6 的 POS_VEL 模式和环路参数只读校验；合法持久增益不要求与 YAML 精确
  相等，读取失败、模式错误或增益无效时不会使能，启动路径不会调用寄存器写入或
  `ensure_mode()`。
- 使用伪时钟验证速度、加速度、加加速度整形对可变 `dt` 仍连续。
- 验证瞬时跟踪误差不会触发，持续 `0.30 s` 才触发保持。
- 验证引导臂超时走“保持—回位”，从臂反馈超时走严重异常。
- 验证可恢复异常绝不直接失能。
- 验证安全位返回失败且电机健康时保持使能并进入 `OPERATOR_RECOVERY`。
- 验证启动不要求跟随就绪姿态，并验证最近实机起点可返回网页停放安全位。
- 验证只有安全位到位并稳定后，或明确严重异常/紧急停机时，才调用失能。
- 验证部分使能失败的回滚和逐关节状态报告。
- 验证夹爪句柄从未收到模式、使能、失能或运动命令。
- 验证所有 SDK 错误都可观察，不被静默吞掉。
- 验证现有只读命令不改变行为，普通测试不会打开真实串口。

### 10.2 静态真机前检查

- 确认两个串口设备身份、波特率和所有节点反馈完整。
- 确认 `/dev/ttyACM0` 的 ROS 占用者已由对应任务正常停止，而非被强制杀死。
- 确认从臂 J1～J6 和夹爪启动状态均为 `status_code=0`。
- 确认当前姿态在真实关节限位内、工作空间无障碍物、操作员可触及急停。
- 输出并人工核对映射符号、基线和本次实际加载的全部阈值。

### 10.3 真机跟随验收

按照操作员要求，不安排逐关节最小运动测试。完成静态检查后直接进入 J1～J6 全轴实时
跟随，由操作员使用引导臂做一系列动作；夹爪保持不受控。

验收记录至少包括：

- 50 Hz 目标下的实际循环频率、P95/P99 周期和超时次数；
- 六轴最大/RMS 跟踪误差以及最大主从滞后；
- 全程位置、速度、加速度、加加速度和状态码是否越界；
- 操作员对姿态方向和实时性的确认；
- 一次正常停止的保持、受控回 `safe_home`、到位稳定和失能验证；
- 不主动制造通信故障、电机故障或坠落风险。严重异常只用伪 SDK 自动测试验证，除非
  后续另行制定安全的台架测试方案并获得明确授权。

自动化测试通过只能证明软件行为。只有本节真机记录完成，才能把本里程碑标记为真机
跟随通过。

## 11. 后续 ROS 2 接入

Python SDK 真机验收完成后，再建立独立的 ROS 2 里程碑。届时复用本设计中的纯函数目标
整形、参数和状态机语义，把硬件生命周期放入 `rebotarmcontroller`，操作员输入适配放入
`rebotarm_teleop`，启动组合放入 `rebotarm_bringup`。ROS 2 版本不得通过导入本独立仓库
的脚本来绕过现有包边界。
